01Platform overview

Encore is a multi-tenant platform for concerts and live venues: ticketing, table ordering, stock, staff and analytics. Organizers run their venue from the admin app; guests book and order from their phones; Encore's own operators watch the whole platform.

Guests · /

Guest web app

Browse organizers and concerts, sign in with a phone code, reserve tickets (a QR per ticket), scan a table, order food and drinks, tip a waiter by badge number, pay by wallet or cash, follow the order, rate the organizer.

Organizers · /admin

Organizer admin

Dashboard, orders (including orders taken by staff), printable receipts and kitchen tickets, bookings and check-in, reports with suggestions and PDF/CSV export, events, menu, stock (store and menu), tables with QR codes, waiters, team roles, settings, and an in-app guide.

Encore staff · /admin/platform

Platform console

Cross-organization analytics, organization management (suspend, reactivate), guests, staff accounts (end sessions, reset password), activity log and system health.

Design principles

  • The server decides. Prices, VAT, service charge, stock, capacity and payment state are always recalculated in domain.py; the browser only previews.
  • Fail closed, never pretend. No demo mode exists in the product: sign-in codes are never shown on screen, and no payment is ever marked paid by the software. Cash is paid only when staff record it.
  • Money is integer cents. VAT uses exact fractions with half-up rounding.
  • Tenant isolation. One workspace document per organization; every staff request is scoped to the signed-in user's tenant.
  • Few dependencies. The backend is the Python standard library plus one database driver.
  • Every state is designed. Loading, empty, error, offline and crash states ship with each screen.

Request lifecycle

Request→Route by path→Origin · JSON · size checks→Session lookup→BEGIN IMMEDIATE→domain.py rule→write_tenant (version+1)→COMMIT→JSON (gzip)
  • Writes are serialized with BEGIN IMMEDIATE (SQLite) or a transaction-scoped advisory lock (PostgreSQL), so two guests can never take the last ticket or the last bottle.
  • Optimistic concurrency: staff actions send the workspace version; a stale version returns 409 and the admin app refreshes.
  • Errors map to status codes: ValueError→400, PermissionError→401, LookupError→404, ApiError(status) for 403/409/429/502/503; anything unexpected becomes a generic 500.
  • Commit before respond, so the client's next request always sees its own write.
  • Housekeeping thread (hourly) deletes expired sessions, codes and stale logs — see §5.

05Database

Relational tables for identity, sessions and cross-tenant data; one JSON document per organization for everything that organization owns.

Why a workspace document? An organization's events, menu, tables, orders, stock and settings change together and are read together. One document keeps every rule in plain Python, makes each staff save atomic, and lets upgrade() evolve the shape without SQL migrations. Writes are serialized and the version column gives optimistic concurrency.

Indexes, pooling and retention

  • Indexes on every runtime lookup: notifications by guest and by tenant, session expiry (all three kinds), users(tenant), invites(expires), audit(tenant, created), otp_log(phone, created), uploads(created).
  • PostgreSQL pool (psycopg_pool, DB_POOL_SIZE, default 8) so requests reuse connections instead of a TCP+TLS handshake each time; without the pool package it falls back to one connection per request.
  • SQLite runs with WAL, foreign keys, busy_timeout=15s and synchronous=NORMAL.
  • Retention (db.RETENTION, applied at start-up and hourly): expired sessions, invites and codes immediately; otp_log after 1 day; read notifications after 180 days; audit rows after 400 days.
  • Migrations are additive and idempotent: CREATE TABLE/INDEX IF NOT EXISTS, plus db.migrate() for new columns. SQL is written once with ? and translated for PostgreSQL.

06Business rules

Everything lives in domain.py: functions take the workspace document, change it, and raise ValueError with a message the reader can act on.

Pricing (quote_order)

total = items + service charge + VAT(items + service) + tip
  • Items are priced from the workspace, never from the client.
  • Service charge (service_for): food & drink orders only, a percentage of the item subtotal, half-up rounding. Never on tickets.
  • VAT (tax_for): 15% by default, added on top, exact Fraction math; it applies to the service charge and never to tips.
  • Tip: money_cents (max 50,000), must match a preset unless custom tips are on; rejected when tips are off. Credited to a waiter when the guest gives a badge number.
  • Worked example: 100.00 items + 10% service (10.00) + 15% VAT on 110.00 (16.50) + 5.00 tip = 131.50.

Payments

PathRules
Online wallet POST /api/checkoutAfroPay is not connected, so this returns 503 PAYMENT_NOT_CONFIGURED and nobody is charged. §15 describes the integration.
Cash, food & drinks POST /api/order payment:"cash"Allowed when payments.cash is on. The order reaches the kitchen immediately, marked unpaid with settlement cash.
Cash, tickets same route, kind:"booking"Allowed when payments.ticketCash is on (off by default): reserve now, pay at the entrance. The booking holds capacity but stays unpaid.
Staff order action staff_orderOwner/Admin/Service. Any table, optional waiter, tip and guest name; Cash, Card at venue, or not paid yet; takenBy records the staff member.
Recording payment action settleCash or Card at venue only — bank transfer is not accepted. Sets paid, settledBy, settledAt and notifies the guest.

Nothing is ever marked paid automatically. An unpaid booking cannot be checked in, and a paid record cannot be cancelled.

Orders

Placed→Preparing→Ready→DeliveredCancelledunpaid only · restores stock

Every order validates the table and menu, checks stock for all lines before deducting any (_take_stock), attaches the waiter, writes the stock log, and notifies staff and guest. Guests see each status change.

Tickets and check-in

  • sold() counts Reserved + Checked in tickets; overselling is rejected inside the write lock.
  • Each ticket carries its own random token; the QR payload is REF:serial:token.
  • checkin_ticket takes a scanned QR or a typed reference (admitting the next unused ticket). Tickets are single use; unpaid or cancelled bookings are refused. usedBy records the staff member and is stripped from guest receipts.

Stock

Menu item stock

  • trackStock, stock, lowStock per item.
  • Orders deduct; cancelling an unpaid order restores.
  • Guests see “Only N left”; sold-out items become unavailable.
  • Action stock: add, remove, set.

Store stock (supplies)

  • inventory: beer, wine, bread, meat… with category, unit (15 built in), cost, supplier, reorder level.
  • Decimal quantities to 3 places (2.25 kg).
  • Action inventory_adjust: delivery (may update cost), used, waste, count.
  • Categories are editable per workspace.

Both write to stockLog (change, resulting quantity, reason, who, when — last 500 entries).

Analytics (src/admin/reportData.js)

Pure functions over the workspace document, shared by the dashboard, Reports, exports and the platform console.

  • buildReport(state, {from, to, eventId}) → summary (gross, net, VAT, tips, service charge, sell-through, check-in rate, attach rate, spend per guest…), previous-period comparison, events, best sellers, slow movers, categories, busiest and top-tipped tables, tips by waiter, weekday × hour heatmap, payment methods, daily series, top guests, latest 10 records, findings and sales suggestions.
  • buildPlatform(tenants, filters) → per-organization reports plus merged platform totals in one currency, concentration and multi-organization guests.
  • Only paid, non-cancelled records count as sales. Identity checked in QA: gross = tickets + food & drinks + service + VAT + tips.

07Authentication and roles

Organizers

Email + password

  • scrypt (N=16384, r=8, p=1, 16-byte salt)
  • Password ≥ 12 characters
  • One-time recovery code (sha256)
  • Cookie 7 days, HttpOnly, SameSite=Strict, Secure in production
  • Invitation links for Admin, Service, Gate
Guests

Phone + SMS code

  • 6 digits, HMAC-SHA256 with the server secret
  • 5 minutes, 5 attempts, resend after 60 s
  • 5 codes/hour per phone, 20/hour per IP
  • E.164 normalization (+251…)
  • Session 30 days, SameSite=Lax
Encore staff

Platform console

  • Separate platform_admins table
  • Created from env or --create-platform-admin
  • 12-hour sessions; 10 sign-ins / 15 min per IP
  • Every action written to platform_audit
  • Cannot be used as an organizer session, or the reverse

  • AfroMessage challenge codes: with AFROMESSAGE_CHALLENGE=1, sign-in uses GET /api/challenge — AfroMessage generates, formats and sends the code and returns it, and send_signin_code() hands that code back so the server stores its HMAC for verification.   • Gateways that answer 200 with an error payload are treated as failures.
  • Prove delivery before launch: python3 server.py --sms-test +251911234567.
  • In development with no provider, messages print to the terminal and are never reported as sent; in production that fallback is refused.

10App states

Loading, empty, error, offline and crash states are part of each screen, not an afterthought.

11Security

Transport and headers

  • HSTS in production; Secure cookies.
  • CSP default-src 'self' with per-file script hashes, frame-ancestors 'none'.
  • X-Frame-Options: DENY, nosniff, Referrer-Policy: no-referrer, camera-only Permissions-Policy.
  • API responses no-store; robots.txt keeps crawlers out of /admin and /api.

Credentials and secrets

  • scrypt passwords; session, invite and recovery tokens stored as sha256.
  • OTP codes are HMACs keyed by ENCORE_SECRET, compared in constant time.
  • Production refuses to start without ENCORE_SECRET and HTTPS origins.
  • data/, .env* and keys are git-ignored; a pre-commit hook blocks credential-shaped strings.

Abuse limits

  • Organizer auth 30 / 15 min per IP; platform console 10 / 15 min.
  • Codes: 20/hour per IP, 5/hour per phone, 60 s resend, 5 attempts.
  • Orders 30 / 15 min per IP and 20 per guest; table lookups 30 / 10 min.
  • Bodies ≤ 7.5 MB; uploads ≤ 5 MB with magic-byte checks.

Data integrity

  • Tenant scoping on every staff query; guest records filtered by guest id.
  • Server-side prices, capacity, stock and tips; serialized writes with versions.
  • Unguessable ticket, table and receipt tokens; single-use check-in.
  • Platform data responses carry no password hashes or tokens; staff names never reach guest receipts.

Tests

  • AppTests — an admin and a guest server on random ports against a temporary database, with a capturing SMS provider: accounts, tenants, events, menu, tables, orders, check-in, tax, platform console, HEAD/robots/gzip.
  • DomainTests — domain.py directly: pricing with VAT and service charge, stock and overselling, store inventory with units, waiters and tips, cash rules, category changes.
  • SmsProviderTests — each provider's HTTP request captured and asserted (including AfroMessage's send and challenge calls and its error replies); unconfigured providers never report success.
  • JourneyTests — longer flows: profiles, uploads, tenant isolation, concurrent bookings.
  • Add a test with every rule change, and run both databases before deploying.

Conventions

  • Business rules only in domain.py; HTTP only in server.py.
  • Integer cents; validate with money_cents(), whole(), number(), text().
  • Error messages are written for whoever reads them — guest or staff — in plain language.
  • New workspace fields get defaults in blank() and upgrade(); new columns go in db.migrate().
  • Never fake a payment or a delivered message; never commit data/, secrets or customer data.
  • Guest app stays mobile-first: check 320, 375 and 768 px plus desktop.

15Extending Encore

Add an SMS provider

# sms.py
def _send_mygateway(phone, text):
    _json_post('https://gateway.example/send', {'to': phone, 'text': text},
               {'Authorization': 'Bearer ' + os.environ['MYGATEWAY_TOKEN']})

PROVIDERS['mygateway'] = _send_mygateway
REQUIRED['mygateway'] = lambda: [n for n in ('MYGATEWAY_TOKEN',) if not os.environ.get(n)]
# then: SMS_PROVIDER=mygateway python3 server.py --sms-test +2519…

A provider that generates its own sign-in codes (like AfroMessage's challenge endpoint) returns the code from send_signin_code(); the server stores whatever comes back. Or skip code entirely and use SMS_PROVIDER=http with a body template.

Connect AfroPay (online payments)

  1. Obtain the merchant API documentation and credentials: payment request, callback signature, status query, refunds.
  2. Add payments.py shaped like sms.py: create a pending payment for a quote and return the redirect or USSD instructions.
  3. Replace the PAYMENT_NOT_CONFIGURED branch of /api/checkout: create the booking or order unpaid with settlement afropay and a payment reference; set PAYMENTS_READY from configuration.
  4. Add a callback endpoint that verifies the signature, then marks the record paid (settledBy, settledAt, wallet) inside a write transaction and notifies the guest. Make it idempotent.
  5. Handle expiry (release capacity and stock) and refunds; add tests with recorded provider responses.

Add a staff action

  1. Add elif op == 'my_action': to domain.mutate() with validation and a readable ValueError.
  2. Allow it for the right roles in STAFF_ROLES; add it to the _by list if the staff member's name should be recorded.
  3. Call it with ctx.action('my_action', data).
  4. Add a domain test, and an AppTests test proving the refusal for roles that must not have it.

Add a report metric or a settings group

  1. Metric: compute it in summarize()/buildReport() (paid, non-cancelled only), show it with Kpi/DataTable, and add it to reportPdfSections and reportCsvRows; add a rule to suggestions() if it should drive advice.
  2. Settings: defaults in DEFAULT_SETTINGS, validation in configure(), expose in public_settings only if guests need it, then a section in Settings.jsx using useDraft and SaveBar.
